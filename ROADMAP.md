# Roadmap

MDL v0.1 is the first public release. It is complete when every box below is
checked. Phases are ordered by dependency: each builds on the previous one.

## Phase 0: foundation

- [x] Repository, dual MIT / Apache-2.0 license, workspace (`mdl` library,
      `morphc` CLI)
- [x] MDL v1 moved from morpheus-c2: TOML frontend, IR, validation, plans,
      bit extraction, interpreter
- [x] Canonical JSON (RFC 8785) for artifact hashing, a strict parser (no
      duplicate keys), the normative rules in
      [spec/canonical-json.md](spec/canonical-json.md), and the first
      conformance vectors (`conformance/canonical/`, generated by V8)

## Phase 1: IR v2 core

- [x] IR v2 types (`crates/mdl/src/v2/ir.rs`): strict reading, normal
      form, `major.minor` versions, API stable under additions
- [x] Strict reader (`v2::read`): canonical checks, version check before
      the shape, typed reading from the canonical form, errors with JSON
      paths, digests
- [x] Artifacts: catalog, family, set; content-addressed by the SHA-256 of
      their canonical JSON; a set records the hashes it was validated
      against; each artifact records the lowest IR version its features
      need (so moving the compiler to 2.1 doesn't change unchanged
      artifacts' identities)
- [x] Families: encoding, byte order, alias and version locators, declared
      metadata
- [x] Layout: absolute and sequential entries, arrays (fixed, counted,
      remaining), reusable struct types, conditional entries, padding,
      variable-length strings and bytes
- [x] Validation for all of the above, with stable diagnostic codes and JSON
      Pointer paths; integers within ±(2^53 − 1); one spelling per instant;
      packet identification where the most specific packet wins
- [x] Catalog compatibility check between versions (additions and
      deprecations only)
- [x] Bindings file format, `Resolver` trait, file-backed resolver, set
      selection (version locator, else binding effective at ground time);
      the sets loaded for one family are checked together (unique versions),
      since stored artifacts can come from more than one build
- [x] Decoder: compiled in-memory program, identification index, record
      tree output, canonical values (composites, array samples), quality

## Phase 2: commands (encode)

Commands come before the frontends, so each importer brings in telemetry
and commands in one pass.

- [x] Canonical commands and arguments in the catalog (types, units, ranges,
      states)
- [x] Command layouts in sets: argument bindings, constants, computed
      lengths, payload checksums (CRC-8 to CRC-64, sum, xor, the ECSS ISO
      checksum)
- [x] The target's native id as a field source, for links that carry it
      in the payload
- [x] Inverse conversions (linear, states, monotonic tables; explicit inverse
      for polynomials)
- [x] Encoder; `encode → decode` round-trip property tests
- [x] Command decoding: a command packet identified by its constants and
      metadata, its arguments decoded (simulators, command history)
- [x] `spec/encoding.md`: the normative encoding rules

## Phase 3: what importers need from the IR

- [x] Calibrations: lookup tables (linear or step, with extrapolation
      policy), natural cubic splines
- [x] Time: Unix (s/ms/µs/ns) and any epoch, GPS week + seconds, time
      scales (utc, tai, gps) with the leap-second table
- [x] Units: UCUM subset with dimensional analysis; a field in a different
      but compatible unit is converted automatically (mV → V, Cel → K)
- [x] Byte order per value, for a little-endian payload behind a
      big-endian header
- [x] Terminated values in fixed-size buffers (a C `char[16]`): the value
      ends at the terminator, the entry takes the whole buffer
- [x] List arguments: a command argument that takes a list of values,
      encoded by an array of values, or of records whose fields take one
      list each; counts fixed, from a field (shared by arrays) or to the
      end

## Phase 4: frontends

A frontend that needs a format library is its own crate, so the `mdl`
core takes on no format dependencies; JSON, the IR's own format, is in the
core. An import is honest: anything the source has that MDL can't
represent is a diagnostic naming the construct and where it is, never a
silent drop ([spec/frontends.md](spec/frontends.md)).

- [x] Source-located diagnostics (file, line, column), shared by every
      frontend
- [x] TOML (MDL's own authoring format), its own crate, with examples,
      including mixed versions on one link
- [x] JSON: the IR itself, in the core, documented as a frontend
- [x] XTCE import, its own crate: telemetry and commands (SpaceSystem, parameter and
      argument types with encodings and calibrators, sequence containers
      with base containers and restriction criteria, MetaCommands); the
      supported subset documented

## Phase 5: `morphc`

- [x] `morphc build`: any frontends merged into one bundle, validated, and
      written to a content-addressed artifact store (rebuilds keep
      unchanged sets' identities); grouped warnings, JSON output
- [x] `morphc inspect`: families and sets with their identities, a set's
      datasheet with every entry's position (from a public layout API), and
      every packet that sends a param or encodes a command
- [x] `morphc decode`: one message or a capture of many, routed with
      bindings or a stand-in, samples or command arguments out
- [x] `morphc encode`: a command and typed arguments to a payload, its
      metadata and def_version
- [ ] A build file listing inputs with their own options (several XTCE
      imports in one build)
- [x] README and examples rewritten around v2: a walkthrough that runs as
      a test, the README's library example run as a doc test
- [ ] Remove v1 (`ir`, `validate`, `interpret`, `plan`, `frontend`, `bits`)
      and move `v2::*` up one level

## Phase 6: hardening

- [ ] A kitchen-sink definition using every IR feature, written in every
      frontend, all producing identical artifacts
- [ ] Real-world corpora: public XTCE definitions imported, validated and
      decoded
- [ ] Differential tests (`just diff-test`, optional, run in CI): traffic
      generated with reference implementations (Yamcs) decoded by MDL and
      compared
- [ ] Fuzzing (`cargo-fuzz`): reader, bindings, decoder, encoder and
      importers, plus generated definitions
- [ ] `encode → decode` and `decode → encode` round trips across the
      kitchen sink

## Phase 7: performance

- [ ] Benchmarks: a small housekeeping packet, a wide packet, a high-rate
      block, a JSON payload, identification across hundreds of packets,
      routing plus decoding end to end; throughput per core and allocations
      per message
- [ ] A baseline, then budgets, then tuning against them
- [ ] Compiled conversions: per-field data worked out once per set (a
      spline's curvature, unit factors) instead of per value
- [ ] Benchmark regressions checked in CI

## Phase 8: interoperability

- [ ] CBOR and MessagePack payloads (JSON Pointer locations)
- [ ] JSON Schema for every IR artifact, generated and checked in
- [ ] Conformance suite: language-neutral cases (artifacts + payload hex +
      expected output or expected diagnostics) and a runner

## Phase 9: language bindings

All bindings share one coarse API: load artifacts, decode, encode, with
results as JSON or CBOR, so each binding stays thin.

- [ ] C ABI (`mdl-ffi`) with a generated header
- [ ] C++ (header-only wrapper over the C ABI)
- [ ] Go
- [ ] Python (PyO3)
- [ ] WebAssembly (browser and Node)
- [ ] Elixir (Rustler NIF)

## Phase 10: release

- [ ] The MDL specification (IR, semantics, canonical form, conformance)
- [ ] User guide (mdBook)
- [ ] CI: fmt, clippy, tests, MSRV, fuzz smoke, `cargo-deny`, conformance
- [ ] Final crate names; publish to crates.io, PyPI, npm, Hex
- [ ] CHANGELOG, CONTRIBUTING, SECURITY, versioning policy
